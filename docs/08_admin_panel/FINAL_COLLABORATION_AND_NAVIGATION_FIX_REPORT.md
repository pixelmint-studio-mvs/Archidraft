## 2. Reproduction Steps & Observed Defects

### Defect A: Collaboration Hub Runtime Rendering Crash
1. As an authorized Studio Admin or Engineer, open any project in the Admin Web Portal at `/projects/[projectId]` (e.g., project `zoro` or `prj-review-001`).
2. Switch to the **Collaboration Hub** tab.
3. When messages or audit events generated by `STUDIO_ADMIN` or `ENGINEER` users are processed, the page crashes with:
   ```text
   TypeError: Cannot read properties of undefined (reading 'bg')
       at getRoleColor (page.tsx)
   ```
4. In addition, the participants card in the Collaboration Hub failed type checking on `p.note` when referencing heterogeneous participant objects.

### Defect B: Cross-Portal Navigation and Link Redirection Errors
1. In the Project Detail page header and Overview card:
   - The ordering Engineer was displayed as raw static text (`project.client_id`) without a clickable route or mapped to `/users` generically.
   - The assigned Draughtsman was displayed without a route to `/draughtsmen/:id`.
2. In the User Directory (`/users`):
   - Clicking a user row with role `ENGINEER` routed to generic `/users` instead of `/engineers/:id`.
   - Clicking a user row with role `CLIENT` or `DRAUGHTSMAN` routed to `/engineers` or `/draughtsmen` root index instead of their specific dossier `/engineers/:id` or `/draughtsmen/:id`.
3. In cross-portal notifications:
   - When a notification or link passed a project ID to the assignment endpoint `/api/assignments/:id`, the Worker strictly filtered `WHERE id = ?`, returning HTTP 404 when given a valid `projectId`.

## 3. Root Cause Analysis

1. **Role Mapping Omission in `getRoleColor`:**  
   In `apps/admin-web/src/app/projects/[projectId]/page.tsx`, `getRoleColor(role)` contained a strict `switch` statement checking only `'ADMIN' | 'DRAUGHTSMAN' | 'CLIENT'`. When comments posted by `STUDIO_ADMIN` or `ENGINEER` were rendered, `getRoleColor` returned `undefined`. Accessing `rc.bg` or `rc.border` caused an unhandled `TypeError` that took down the entire tab.
2. **Author Role Normalization in `toCollabMessage`:**  
   Raw database rows from `project_comments` and `activity_logs` contained diverse actor roles (`STUDIO_ADMIN`, `ADMIN`, `ENGINEER`, `CLIENT`, `DRAUGHTSMAN`). The translation layer did not normalize `STUDIO_ADMIN` to `'ADMIN'` or `ENGINEER` to `'CLIENT'`, and lacked safe author name fallbacks.
3. **Broken Profile Navigation Targets in Directory and Project View:**  
   `apps/admin-web/src/app/users/page.tsx` constructed `profileHref` as `u.role === 'CLIENT' ? '/engineers' : u.role === 'DRAUGHTSMAN' ? '/draughtsmen' : ...` omitting the required `:id` parameter, and sent `ENGINEER` roles to `/users`.
4. **Worker Assignment Route ID Sensitivity:**  
   In `worker/src/index.ts`, `GET /api/assignments/:id` only matched assignment primary keys (`WHERE a.id = ?`). Cross-portal Flutter workflows that reference the assignment by project ID failed to resolve the active assignment record.

## 4. Remediation & Code Changes

### A. Frontend (`apps/admin-web/src/app/projects/[projectId]/page.tsx`)
- Updated `getRoleColor` to explicitly handle `'ADMIN'`, `'STUDIO_ADMIN'`, `'DRAUGHTSMAN'`, `'CLIENT'`, `'ENGINEER'`, and `'STUDENT'`, and added a safe fallback object `{ bg: '#f1f5f9', text: '#475569', border: '#cbd5e1' }` so it **never** returns `undefined`.
- Updated `toCollabMessage` to normalize `STUDIO_ADMIN` to `'ADMIN'` and `ENGINEER` to `'CLIENT'`, providing robust author name fallbacks.
- Updated Project Header, Overview Tab, and Assignment History Tab:
  - Header displays clickable links: Engineer links to `/engineers/${project.client_id}`, Draughtsman links to `/draughtsmen/${project.draughtsman_id}`.
  - Overview tab links "Ordering Engineer" to `/engineers/${project.client_id}` and "Assigned Draughtsman" to `/draughtsmen/${project.draughtsman_id}`.
  - Collab Hub Participants card links directly to respective dossiers.

### B. User Directory (`apps/admin-web/src/app/users/page.tsx`)
- Updated `profileHref`:
  - `CLIENT` and `ENGINEER` -> `/engineers/${encodeURIComponent(u.id)}`
  - `DRAUGHTSMAN` -> `/draughtsmen/${encodeURIComponent(u.id)}`
  - `STUDENT` -> `/students/${encodeURIComponent(u.id)}`
  - All other roles link safely to `/users` with fallback.

### C. Backend Worker API (`worker/src/index.ts`)
- In `GET /api/projects/:id` and `GET /api/projects/:projectId`, added `LEFT JOIN users u ON p.client_id = u.id` to return authoritative `client_name` and `client_email`, plus subquery resolution for `current_assignment_id`.
- In `GET /api/assignments/:id`, enhanced query to match either assignment ID or project ID:
  ```sql
  WHERE a.id = ? OR a.project_id = ?
  ORDER BY (CASE WHEN a.id = ? THEN 1 ELSE 2 END), a.created_at DESC
  LIMIT 1
  ```
  Preserves strict RBAC: only assigned draughtsmen, project owner, or studio admin are authorized to read the record.
